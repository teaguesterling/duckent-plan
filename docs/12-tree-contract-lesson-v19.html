PRELUDE

Two tables you already have

DEPLOYED

A family of extensions loads hierarchical data into ordinary DuckDB tables: sitting_duck (ASTs, 27 grammars), webbed (XML/HTML), panduck & duck_block_utils (Markdown, DOCX, PDF). No pointers, no nested types, no document store — rows. Here is the same pattern from two very different producers.

A Markdown file through read_markdown_blocks becomes a block per row: type, nesting level, source order, content — the duck_block table format that duck_block_utils, panduck, and the markdown extension all share. A Python file through sitting_duck becomes a node per row (output schema): type, depth, DFS order — plus native extras like descendant_count — and CSS selectors already query it. Compare the two schemas and the same skeleton appears in both: rows in traversal order, a nesting column, a type column. Everything else — ids, attributes, counts — varies by producer. That shared skeleton is not a coincidence, and taking it seriously is what the rest of this lesson does: first by hand (Lessons 1–3), then as a contract (Lesson 4), then as syntax (Lessons 6–8).

That is also the order the work happened in, and the order is the argument. We started with ASTs and CSS: sitting_duck put selectors on source code, and it worked. Then we went backwards, to where CSS came from — HTML — and brought along everything already modeled as duck_blocks: Markdown, DOCX, PDF, not just HTML, with no conversion to or from HTML at any point. The duck_block tree handled it as it stood. Your documents were rows too. Only then did we ask the question this lesson is organized around: what do ASTs and duck_blocks actually need to be trees, what does CSS need on top of that to have anything to say, and what is there only to make it fast? Those three answers are R, S, and O.

LESSON 2

  
sitting_duck, as it ships

  

    

      

        
Start with the table function read_ast('src/**/*.py'): it returns your codebase as rows — node_id, parent_id, type, depth, descendant_count, semantic_type — across 27 tree-sitter grammars. The taxonomy is the point: semantic_type_to_string(semantic_type) = 'DEFINITION_FUNCTION' means function-definition however your grammar spells it, so one query spans Python, Rust, and JavaScript without editing a type name.

Custom pseudo-classes are SQL macros — :docblock is a macro whose body is itself a selector, so grammar-specific structure hides behind one portable name.

LESSON 3

  
The encoding: a tree as its own traversal

  

    

      

        
Node IDs are depth-first order, so structure is adjacency: anchored at a body block, a documented function is three consecutive rows — block, expression_statement, string — and DuckDB's window machinery reads it (with parentage verified, not just position). First-child is an aggregate: min(node_id) per parent; arg_min(type, node_id) reads its type.

        
This encoding has a name and a history: pre/size/level, from the XML-database era — Grust's XPath accelerator, MonetDB/XQuery's Pathfinder. sitting_duck's node_id / descendant_count / depth is that table column for column, converged on independently. That history pays off directly: DuckDB's recently optimized recursive CTEs (USING KEY, from the same Tübingen group) are about to matter below.

The pattern as a row value. Grep scanned adjacent lines; this scans adjacent rows with types — and everything joins.

        

      

    

  






  
LESSON 4 · R

  
Required: what makes rows selectable

  

    

      

        
The selector engine never needed pointer-linked trees. The tree is real; the pointers were optional — what it consumes is rows under three requirements. R1: order matters. R2: a structural basis of level | parent — either one, each derivable from the other. A level column obeys level[n+1] ≤ level[n]+1 (descend at most one, pop freely — that invariant alone characterizes a forest); a parent column derives (order, level) via one recursive CTE, needing a sibling sort key and the root-unique column PARENT refers to — without the sort key the source conforms to the sibling-free profile (+, ~, :first-child refused legibly, everything else intact), and without the unique column the declaration is refused outright: "tree_ddl_create: PARENT basis requires UNIQUE KEY (the column PARENT refers to)". That's the whole of it: R1 + R2 are the minimal treeness set — everything else in the contract is about what you can say or how fast you can say it. A type accessor isn't required for trees at all, only for CSS-style selection — so it lives in S (as S0°, defaulting every node to type node), and a typeless tree still matches structurally. And R0°, spelled ROOT (col, …), is required iff the relation holds more than one tree: tree-identity columns, constant per tree — delimiting forests, keying tree-granular DML (INSERT OR REPLACE by ROOT = re-derivation; never row surgery), feeding ATTACH. Absent, the relation is one tree; per-tree order resets without ROOT are rejected outright. Accessors may be bare column reads.

LESSON 4 · S

  
Semantics: what selectors can say

  

    

      

        
First, the base slot: S0°, TYPE — total, defaulting every node to type node, because selection needs a type dimension even when trees don't; declare it and type selectors light up. The rest of S is the expressive surface, and here the two vocabularies part company: selector syntax is CSS's, and the catalog's vocabulary is duckent's. A selector still writes #main, .fn, [lang="py"], :leaf — those spellings are thirty years old and not up for renaming. What a tree declares is named for what it is: KEY is the row's own label, which # matches (at most one per row and not unique — the root-unique column is R's UNIQUE KEY, a different slot); TAGS is zero or more labels per row, matched as a set, which . matches; ELEMENT says which rows are elements when not every row is one.

        
Attributes come in two tiers. ATTR is the named, typed tier — real columns, so a comparison runs in the column's own type — and ATTR_MAP is the catch-all for the long tail, supplied as a MAP. Named wins; the map serves undeclared names; neither declared → refused legibly. Rule of thumb: hot attributes earn names; the map is for the tail, not the hot path. CSS's own attribute grammar is the limit on how much of that a selector can reach: v0 parses =, ^=, $= and *= and nothing else, so [start_line>100] is not a selector at all — the front-end refuses it with "css: expected one of = ^= $= *= after attribute start_line". A numeric comparison is spelled in TREEQL (ATTR start_line > 100) or minted as a predicate; the extended operator set is v1.

        
And the extension mechanism, which is what PREDICATE declares — not a slot, but a registry the catalog keeps in tree_catalog_predicates(). A predicate is bound per tree, in one of four forms: an expression body, a macro plus its arguments, a {prefix} binding that enumerates every catalog macro carrying that prefix, and a shared sel_* tier scanned for every tree — tree-local shadowing shared, so :docblock can mean the right structure per grammar without collision. The predicate name is the method, the tree is the type, the macro is the instance; ambiguity is refused at registration, not discovered at match time. Each body's purity is computed at declaration and recorded: a body reading a VOLATILE function is refused outright, and a macro that calls a macro is recorded unknown rather than guessed at.

LESSON 4 · O

  
Optimizations: cost only, never results

  

    

      

        
O slots buy speed: the non-native basis member, subtree size, child count, next sibling (pre+size+1). Each has a default derivable from (order, level); native columns register as overrides — and every override must test-equal its default. An override that changes a match set is not a fast path; it is a corrupted encoding, flagged at that severity. That is a running assertion, not a slogan: a declared SIZE, CHILDREN or NEXT is compared against its derivation at ingest, tree_check re-runs the comparison and records assert_o_size / assert_o_children / assert_o_next, and a disagreement is refused with the offending root and position named — "declared 0, derived 2 (a corrupted encoding, not a fast path)". The suite 42_second_differential.test runs the whole selector corpus against a declared-O tree and a derived-O tree and requires the same rows from both.

        
The refinement that turns this from rule into theory: the R/O split has a criterion. Type, key and tags are row-local — they depend on nothing but the row. Every O member is row-transcendent: its value summarizes other rows, and that dependence is exactly what scopes it. Within one tree, that scope is its ROOT partition, and the prototype enforces it: no adjacency, subtree or sibling test crosses a ROOT boundary, which is what mutant MN14 exists to prove.

        
DESIGN, NOT BEHAVIOUR · THE O NAMESPACE
The design goes further than the build: O values would be namespaced to (taxon, load-watermark) — valid within their own tree's materialized extent, never across an attachment splice (a parent tree's descendant_count cannot see attached forests), never above an unloaded frontier — so that a namespace-checked read yields a Bound and a mismatched read an Estimate, with estimates free to inform join order and never results. None of that is built. The words Bound, Estimate, taxon and watermark appear nowhere under sql/, because the thing they scope — the W block — is unbuilt too. The XML era fought this as the dynamic-update problem and answered with renumbering; the contract intends to answer with locality, and mutants MN10 and MN11 are the tests waiting for it.

        
CASE STUDY · WHY duck_blocks SHIPS NO O
sitting_duck stores parent ids and descendant counts natively; duck_block_utils stores neither — and both are right. ASTs are deep (one function can be hundreds of nodes) and queried structurally, so O pays daily. Document blocks are bigger, flatter, and spliced constantly — assembled, sliced, concatenated — and id-free, O-free rows compose by concatenation; O columns would be perpetually stale under that splice rate. Omitting O isn't a gap. It's the correct point on the depth × splice-rate tradeoff, and the contract holds both ends.

LESSON 4 · W

  
World: linking trees without touching them

  

    

      

        
WHOLLY DESIGN
Everything in this lesson is design. No W slot exists in the prototype's TREE_SHAPE type; the catalog carries an empty tree_catalog.attachments table and nothing writes to it; and W's four mutants — MN09, MN10, MN11, MN16 — are named and not planted. Read the laws below as the specification the tests will be written against, which is what doctrine 3 asks of a claim with no test behind it.

        
Trees link to other trees, and the linkage has laws. W1: attachments are root-restricted foreign keys — child-tree roots reference parent-tree nodes, interior nodes never do (that restriction keeps ancestry a forest, not a graph), and the child root splices in at level(parent)+1. W2: loaders — demand materialization with a tri-state frontier (loaded / unloaded / absent; the distinction matters). Both are parent-parameterized: bindings are deterministic functions of the parent row's local columns — a code fence's language attr selecting the parser is the archetype. W3: epoch manifests, provenance keyed by (parent, params), refresh by selector.

        
The governing law, W-locality: within-tree match sets are invariant under any change to W. Attach, detach, load, refresh — a single tree's answers never move. W belongs to binding, planning, and provenance; never to semantics. And dangling references are drift telemetry, not errors: absence at a frontier is a fact.

LESSON 6

  
duckent I — CREATE TREE: speaking Tree, fluently

  

    
EXPERIMENTAL

    

      

        
DuckDB 2.0's runtime-extensible PEG parser lets extensions add syntax and reuse the rest of SQL — so the ROWS contract becomes DDL. The shape specification is the contract, slot for slot, and it scales from two lines to full dress. Minimal: one slot makes rows a tree — type defaults to node, so * and every structural combinator already work. Typical: an abstract tree (SHAPE ONLY — required whenever there's no AS, so sourcelessness is declared intent, never an accident) instantiated with LIKE, which copies semantics, never source — the universal LIKE contract. Full dress adds the S tiers and O declarations.

        
Read the full-dress figure as a tour of the blocks: ROOT is tree identity (R0); LEVEL the structural basis, with PARENT the alternative that also wants a UNIQUE KEY to refer to; TYPE, KEY, TAGS and ELEMENT the S slots a selector reads as fn, #name, .fn and "is this row an element at all"; ATTR the named, typed tier (bulk-bindable via COLUMNS('a_(.*)') AS '\1') over an ATTR_MAP catch-all; and PREDICATE binds predicates per tree — the value is an ordinary expression in the tree's row scope, exactly like a generated column or CHECK constraint, so calling a macro is just calling it: docblock := has_docblock(file_path, node_id). No lambda syntax, no binding machinery — SQL already knows how to evaluate an expression per row. A PREDICATE PREFIX pulls in a whole shared library, shadowed by anything tree-local. And every OPTIMIZE annotation auto-generates its conformance assertion: an O override that diverges from its derivable default is flagged as corruption, not speed.

        
Miss a capability and the refusal is legible at bind time — but the granularity is the SEMANTIC group, not the individual slot. Query a tree that declares no S at all and .fn, #x, module and :leaf all give you the same sentence, which is the one the prototype actually prints: "tree_match: tree main.org has no SEMANTIC group; only combinators and WHERE are available. Add one with tree_ddl_alter or pass semantic :=". Note what it does besides complaining: it names the two things that do still work on a tree with no semantics, and the two ways to give it some.

      

      

        
⧉
          
-- minimal: one slot makes a tree
CREATE TREE toy (LEVEL depth)
  AS FROM read_csv('toy.csv');

-- typical: abstract shape + instance
CREATE TREE sitting_duck_ast (
  SHAPE ONLY,
  ROOT (file_path),

          semantic_type),

  AS FROM read_ast('src/**/*.py');

          
          
SHAPE ONLY declares abstractness; LIKE instantiates. Semantics copy; source never does. An abstract tree is only a shape — it has no rows, so it cannot be queried; the thing you query is the LIKE instance.

        

        
⧉
          
-- full dress: the whole contract
CREATE TREE full (

  LEVEL depth, UNIQUE KEY node_id,
  TYPE t, KEY name, TAGS classes,
  ELEMENT is_element,
  ATTR (COLUMNS('a_(.*)') AS '\1'),

Every OPTIMIZE ships its own conformance test. Named attrs are typed; the map is string-only. UNIQUE KEY is what a PARENT declaration refers to, and is not the S-block KEY that # matches.

        

      

    

  






  
LESSON 7

  
duckent II — MATCH, and the query it abstracts

  

    
EXPERIMENTAL

    

      

        
Think of MATCH as Lesson 3, automated. The selector compiles into exactly the machinery you hand-wrote there — the QUALIFY windows, the grouped firsts, the anti-joins — generated against whatever a tree's shape declares. That's what "abstracts sitting_duck" means precisely: sitting_duck's ast_select is the special case where the basis is level, the O columns are native, and the vocabulary is the code taxonomy; MATCH is the same compilation, parameterized by any shape. Semantics consult declarations — R, S, and attachments — never state, so the answers can't depend on caches or load timing.

        
And the two bases earn their existence here. Level basis is what a producer emits when it already walks the structure — a parser streams DFS order and depth for free, which is why sitting_duck stores node_id/depth/descendant_count natively (pre/size/level: deep trees, structural queries daily, so the O columns are worth storing). Parent basis is how the world's data already sits — every org chart and category table is an adjacency list — and the recursive CTE that DFS-numbers it (fast under USING KEY) is the encoder. You can write it once to understand it; then the DDL internalizes it and you never write it again.

      

      

        
⧉
          
FROM code
MATCH '.fn:not(:has(:docblock))'
SELECT name, start_line;
-- compiles to rung 0's shape:
-- windows, firsts, ANTI JOIN

-- ad hoc, no CREATE needed:
FROM 'code.parquet'
USING TREE SHAPE sitting_duck_ast
MATCH '.fn:not(:has(:docblock))';

          
          
MATCH over a created tree, or USING TREE SHAPE over a bare source — same compiler, USING SAMPLE-style modifier.

        

        
⧉
          
-- adjacency, by hand (the encoder):
WITH RECURSIVE org AS (
  …DFS numbering over manager_id,
   ordered by hire_date… )
-- adjacency, internalized:
CREATE TREE org (
  UNIQUE KEY email,
  PARENT manager_email,
  SIBLING ORDER (hire_date),
  TYPE role, KEY email
) AS FROM employees;

FROM org
MATCH 'manager:has(> engineer)'
SELECT email;

          
The recursive CTE vanishes into the DDL. Level when the producer walks; parent when the data already sits that way; each derives the other. A PARENT basis takes two companions: UNIQUE KEY, the column PARENT refers to — omit it and the declaration refuses, "PARENT basis requires UNIQUE KEY" — and SIBLING ORDER, without which the tree conforms only in the sibling-free profile.

        

      

    

  






  
LESSON 8

  
duckent III — MATCH ∘ SQL: one pipeline, one host door

  

    
EXPERIMENTAL

    

      

        
MATCH is a clause, not a function. Bare, it flows straight into the pipeline you already know — FROM … USING TREE SHAPE … MATCH WITH css … SELECT … WHERE … GROUP BY — terminated by the next clause keyword, scanned outside balanced brackets. No outer string literal, so quote-doubling dissolves. And because the shape projection is the matcher's view, not the result type, MATCH emits raw rows: the WHERE after it is ordinary SQL filtering on everything the source knows, no attribute macros required.

        
CSS's attribute operators run out early — v0 has =, ^=, $= and *=, so a numeric comparison is already past the edge, never mind subqueries and BETWEEN — and when they do, SQL does not go into CSS. CSS stays wholly portable: it extends by pseudo-classes, and minting one is a declaration, not a hack — declare PREDICATE (busy := children_count > 2) and :busy exists. The host door is a second language on the same matcher: MATCH USING TREEQL, one step per line, each a combinator keyword plus parenthesized clauses — TYPE, ID, CLASS, ATTR, PSEUDO — plus a native WHERE that is arbitrary SQL against that step's projection row (closed shapes still refuse undeclared columns: power added, visibility unchanged). AS y names a step, and a named step is a joined alias you can read dotted in the SELECT after the match. The boundary doctrine, quoted in every refusal: CSS extends by pseudo-classes; TREEQL integrates the host; never both in one language.

        
One last collision, from our own toolchain: the taxonomy's 28th grammar is SQL itself, whose trees contain select nodes. Keyword-typed selectors quote like identifiers — MATCH "select" > "from" — and the pipeline keeps flowing. And TREEQL is more than language number two: every registered language normalizes to it, and that normal form is what you can read back. Today it reads back through tree_explain(sch, nm, sel), which returns the TREEQL and the SQL without running either; after 2.0 it is what EXPLAIN MATCH prints. Cross-language differentials compare those normal forms rather than pairs of fixtures.

LESSON 9

  
duckent IV — forests, attachments, virtual worlds

  

    
EXPERIMENTAL

    

      

        
Forests and DML. ROOT makes DML tree-granular: append trees, drop trees by key, and INSERT OR REPLACE is re-derivation — re-parse a file, replace its tree, epoch bumps. Within-tree row surgery doesn't exist; the 2004 renumbering problem is answered by granularity: renumbering never crosses a partition you didn't wholly replace.

        
Attachments. Trees link by root-restricted foreign key — child roots reference parent nodes, interior nodes structurally can't (their only cross-tree coordinate is ROOT, constant per tree) — splicing in at level(parent)+1, with bindings that are deterministic functions of the parent row: a code fence's language attr selecting the parser is the archetype. The first thing attachments buy is ontology mapping: shared reference trees — NCBI's tree of life, WordNet, HS tariff codes — attached many-to-one, every row that names a concept keying into one taxonomy, with subtree membership as a pseudo-class; if you've ever shipped a closure table, you already built that tree's O-block. The second is the analytics workhorse, hierarchy × facts: every subtree rollup today is the same three-part boilerplate — recursively collect descendant ids, semi-join the fact table, aggregate — rewritten per hierarchy, per question. Attach the facts to the tree once and the boilerplate becomes one selector plus one aggregate. (Chains extend arbitrarily far — network to service to file to AST — each boundary a loader; the details are in the field guide.)

        
Virtual trees. Trees too large to materialize whole: materialize two levels, load branches on demand — selector pushdown decides which branches, unloaded is distinct from absent, and matching must equal the fully-materialized ideal within the selector's scope (so demand loading is an evaluation strategy, never a semantics change). Refresh is by selector; every load carries an epoch manifest.

Tree-granular; OR REPLACE = re-derivation by key. Never row surgery.

Everything through M4's introspection now runs as a macro prototype on DuckDB 1.5.5. Here is what exists, what building it proved, and where the next line of code goes.

  

    
EXPERIMENTAL

    

      

        
As of this revision, M0, M1, M1½, M2 and M3 run, and so does M4's introspection layer. The duckent repository holds them as SQL macros under sql/: a catalog of shapes and trees, the projection compiler onto the canonical columns, both basis derivations, forest DML with P13 checked on ingest, a match compiler with captures and nested HAS/NOT groups, two CSS front-ends bound to each other by a row-level differential, the O layer with its conformance assertions, four predicate binding forms with a shared sel_* tier, and the catalog views that the cheatsheet is generated from. Every mutating operation is a pure tree_compile_* macro that returns SQL text; a small Python runner executes it today, a bound table function will in the extension. Twenty-five sqllogictest files run 1,492 assertions with no failures, and all twenty planted mutants die — and the same .test files are meant to run unchanged against the C++ build.

        
Building it settled things the design could not. The derived _parent and _size equal sitting_duck's native parent_id and descendant_count on every row of both parquet fixtures, which is the O law holding on real data — and M3 turned that from an anecdote into a suite, 42_second_differential.test, which runs the whole selector corpus against one tree whose SIZE, PARENT and CHILDREN are declared columns and one that derives all three, and requires the same rows from both. DuckDB's query() refuses text from any macro whose body contains a SELECT, which is why the compilers that must read the catalog are executed by the runner rather than fed to it. A partitioned row_number() without ORDER BY does not preserve scan order, so frozen order captures the scan sequence first. And the harness did its job: two mutants survived their first run, and the answer was a multi-root test and a re-scoped mutant, never a manifest edit.

        
M3 also priced the derivation, and the number is the argument for O existing at all. Deriving _size as a correlated min was quadratic in the rows under one root: a whole-repository parse of 142,651 rows under a single ROOT took 26.9 s derived against 0.23 s declared. Replacing it with a level-expanded ASOF join brought that to 0.28 s — 1.2× the declared column rather than 167× — and left the known-worst shape (100k shallow rows beside a 2,000-level spine) unmoved at 21 s, which is exactly the source the comment on tree_sql_size_join() tells you to declare SIZE on. O is not decoration; the derivation is a convenience with a measured ceiling, and the C++ port's single stack walk is what removes it. The numbers and the shapes are in FINDINGS.md.

        
The review that gated the merge found the defect the tests had not: tree_ddl_alter rebuilt a tree from its create-time source and silently dropped every partition ingested since. It now refuses, naming the partitions and the way around. That is doctrine 3 and doctrine 4 in one finding, and it is the kind of thing the FINDINGS file exists to record.

        
M2's gate was the differential against shipped ast_select, and it is met: 107 of the 108 frozen astcss-eval references are asserted and pass, with the 108th adjudicated against upstream in FINDINGS.md — sitting_duck's bare type selector turns out to prefix-match, so lambda also selects lambda_parameters, which is now filed as sitting_duck #151. A differential is worth having precisely when it can come out that way round.

        
Next is M-LANG: the TREEQL text parser and the language-registration API (D-N10). Today a TREEQL selector is handed over as IR — tree_steps(…) — and passing it as text refuses with "tree_match: TREEQL text parsing arrives with M-LANG; pass tree_steps(...)", which is doctrine 4 standing in for a parser. After that, the W block, which is still wholly design: nothing under sql/ declares a W slot. And then the C++ port, which replaces the derivations' recursive CTEs with one stack walk over pre-order — what "a tree is its own traversal" means operationally, and what turns the size derivation's measured ceiling into an O(n) guarantee. If you want to help, the specs and the plans are in docs/superpowers/, the open decisions are where a second opinion is worth the most, and issues and pull requests are welcome; so is a note.

The macro bridge: what MATCH compiles to, running today
Pre-2.0, the whole DDL compiles to two table macros. A shape is a projection macro onto canonical columns, and there are thirteen of them, every one present whether its slot was declared or derived: _root, _pre, _level, _parent, _size, _children, _next, _type, _key, _tags, _attr_map, _element, _predicate — read out of tree_canonical_columns(). MATCH generates its query against those columns and nothing else. Below is the flagship selector written out by hand, in the shape the compiler emits, so that the mechanism is visible: it is not the compiler's own text, and the figure is here to be read rather than to stand in for it. Both statements were run on DuckDB 1.5.5 with sitting_duck, against the prelude's app.py.
LOAD sitting_duck;
CREATE TABLE app AS FROM read_ast('app.py');

-- a SHAPE compiles to a projection macro onto canonical columns
CREATE MACRO shape_ast(src) AS TABLE
  SELECT file_path AS _root, node_id AS _pre, depth AS _level,
         semantic_type_to_string(semantic_type) AS _type, name AS _key,
         descendant_count AS _size, parent_id AS _parent,
         (flags & 6) = 6 AS _element,        -- ELEMENT: which rows are elements
         type AS node_type, start_line
  FROM query_table(src);

-- MATCH '.fn:not(:has(:docblock))' compiles against the canonical columns only
CREATE MACRO match_fn_without_docblock(src) AS TABLE
  WITH n AS (FROM shape_ast(src)),
  docblock AS (   -- :docblock = block > expression_statement:first-child > string:first-child
    SELECT b._pre, b._size FROM n b
    JOIN n e ON e._parent = b._pre AND e._pre = b._pre + 1   -- first child: next row in pre-order
    JOIN n s ON s._parent = e._pre AND s._pre = e._pre + 1
    WHERE b.node_type = 'block' AND e.node_type = 'expression_statement' AND s.node_type = 'string')
  SELECT f._key AS name, f.start_line
  FROM n f
  WHERE f._type = 'DEFINITION_FUNCTION' AND f._element      -- .fn
    AND NOT EXISTS (FROM docblock d                         -- :not(:has(…)) over the pre/size range
                    WHERE d._pre BETWEEN f._pre + 1 AND f._pre + f._size);

FROM match_fn_without_docblock('app');

The encoder: parent basis → (order, level), in full
The lesson figure elides the recursive CTE to three dots. Here it is whole, run on DuckDB 1.5.5 with USING KEY. Every adjacency list in your warehouse conforms through exactly this query, and CREATE TREE org (UNIQUE KEY email, PARENT manager_email, SIBLING ORDER (hire_date), …) is the promise that you never write it again. The UNIQUE KEY is not decoration: it is the column PARENT resolves against, it is what the walk below joins on, and a PARENT declaration without one is refused outright.
CREATE TABLE employees(email VARCHAR, role VARCHAR, manager_email VARCHAR, hire_date DATE);
INSERT INTO employees VALUES
 ('ada@co','cto',NULL,'2019-01-07'),
 ('bo@co','manager','ada@co','2020-03-02'),
 ('cy@co','manager','ada@co','2019-06-11'),
 ('di@co','engineer','bo@co','2021-09-20'),
 ('ed@co','engineer','bo@co','2020-11-16'),
 ('fay@co','engineer','cy@co','2022-02-01'),
 ('gus@co','intern','fay@co','2024-06-03');

-- the encoder: parent basis -> (order, level); sibling key = hire_date
WITH RECURSIVE walk USING KEY (email) AS (
  SELECT email, role, manager_email, 0 AS level,
         [row_number() OVER (ORDER BY hire_date, email)] AS path
  FROM employees WHERE manager_email IS NULL
  UNION ALL
  SELECT e.email, e.role, e.manager_email, w.level + 1,
         w.path || [row_number() OVER (PARTITION BY e.manager_email ORDER BY e.hire_date, e.email)]
  FROM employees e JOIN walk w ON e.manager_email = w.email
)
SELECT row_number() OVER (ORDER BY path) - 1 AS node_id,
       level, role AS type, email AS id, manager_email AS parent
FROM walk ORDER BY node_id;

TREEQL: a keyword match language over the S block
One step per line, each a combinator keyword plus parenthesized predicate clauses. The clause keywords are CSS's, spelled out. ID is what # means, CLASS what . means, PSEUDO what : means — TREEQL is the selector language with the punctuation replaced by words, which is exactly what makes it a canonical form for every front-end that lowers to the same IR. It is not a second spelling of the declaration, and an earlier revision of this page said it was. Three of the five resolve against a slot with a different name: ID 'parse_ast' is answered by the tree's KEY slot, CLASS 'fn' by its TAGS slot, and PSEUDO 'leaf' by a PREDICATE declaration — which is not a slot at all. That is the naming rule the README states and this table now obeys: selector syntax is CSS's; the catalog's vocabulary is duckent's. A query says what a selector says; a declaration says what the data is. Collapsing the two was convenient while the two vocabularies happened to agree, and it stopped being true the moment the slots were named for what they hold rather than for the punctuation that reaches them.

grammar sketch; the first step takes no combinator (D-N12), like the first FROM item
match_treeql := 'MATCH' 'USING' 'TREEQL' step+
step         := combinator? '(' clause (',' clause)* ')' ('AS' ident)?
              | combinator                          -- bare step = any node
combinator   := 'CHILD' | 'DESCENDANT' | 'SIBLING'   -- adjacent (+)
              | 'FOLLOWING'                        -- (~)
              | 'SELF'    -- first step of a HAS/NOT group only
clause       := 'TYPE' expr | 'ID' expr | 'CLASS' expr
              | 'ATTR' comparison | 'PSEUDO' expr | 'WHERE' expr
Semantics by desugaring: each step is a join against the same projection; the combinator compiles to a structural predicate over the basis (CHILD: parent equality; DESCENDANT: the pre/size range; SIBLING: adjacency under the same parent). Clauses compile to S-accessor predicates. Bare-safe by construction: every step opens with a keyword or a parenthesis, so no token collides with clause-keyword termination.

The four that fall away have none, and that is the point — and it is worth being precise about which four, because an earlier revision of this page drew the contrast and then spelled the uncopyable step in CSS anyway. A step WHERE is arbitrary SQL, so of course CSS cannot hold it. But SIBLING (ATTR start_line > 100) cannot be spelled in CSS either: the v0 grammar's attribute operators are exactly =, ^=, $= and *=, so [start_line>100] is not a selector, and both front-ends refuse it — the runner parser with "css: expected one of = ^= $= *= after attribute start_line", the SQL front-end with "css: unclosed [ in attribute selector", which is tree-sitter-css reading the same text and failing one token earlier. The extended operator set is v1; until then a numeric comparison lives in TREEQL's ATTR or behind a minted predicate. CSS is the portable, corpus-rich surface (browser muscle memory, Text-to-ASTCSS); TREEQL is the one that can afford a ten-line pattern, a typed comparison and a host predicate. Result-set WHERE, SELECT, and GROUP BY follow bare, unambiguous because a step-level WHERE is always parenthesized.

Every registered language normalizes to TREEQL. Promotion from predicate to tag is the sanctioned migration, and P23 certifies it; mutant MN25 is the one that answers a CLASS clause from a predicate of the same name when the row's tag list is empty, which is promotion recomputed at match time.

W: the laws of linking
lawstatementconsequence
W1 — attachmentsA child tree's root references a parent-tree node via a root-restricted foreign key and splices in at level(parent) + 1. Interior nodes structurally cannot: their only cross-tree coordinate is ROOT, constant per tree.Ancestry stays a forest, not a graph. ATTACH child TO parent.node infers the join from ROOT ↔ the parent's ID accessor; USING (…) covers mismatches only.
W2 — loadersDemand materialization with a tri-state frontier: loaded / unloaded / absent. Bindings are deterministic functions of the parent row's local columns (a code fence's language attribute selecting the parser is the archetype).Matching must equal the fully-materialized ideal within the selector's scope (P20), so a loader is an evaluation strategy, never a semantics change.
W3 — epochsEvery load carries an epoch manifest; provenance is keyed by (parent, params); refresh is by selector.REFRESH TREE fs BRANCH 'dir#var' reloads exactly the branches the selector reaches.
W-localityWithin-tree match sets are invariant under any change to W. Attach, detach, load, refresh: a single tree's answers never move.W belongs to binding, planning, and provenance; never to semantics. MN9 (an attachment changes a single-tree match set) must die.

Example 2, run today: the boilerplate the attachment replaces
The chart-of-accounts rollup is the community's canonical clunky-CTE case. Below, the boilerplate as it stands on DuckDB 1.5.5, with real numbers, followed by the duckent IV spelling.
CREATE TABLE coa(account_id INT, name VARCHAR, parent_id INT);
INSERT INTO coa VALUES (1,'root',NULL),(2,'opex',1),(3,'salaries',2),(4,'travel',2),
                       (5,'capex',1),(6,'servers',5),(7,'airfare',4);
CREATE TABLE ledger(entry_id INT, account_id INT, fy INT, amount DECIMAL(12,2));
INSERT INTO ledger VALUES (1,3,2026,120000),(2,7,2026,4200),(3,6,2026,80000),
                          (4,3,2025,110000),(5,4,2026,900);

-- today: collect descendant ids, semi-join the facts, aggregate. Per hierarchy. Per question.
WITH RECURSIVE under_opex AS (
  SELECT account_id FROM coa WHERE name = 'opex'
  UNION ALL
  SELECT c.account_id FROM coa c JOIN under_opex u ON c.parent_id = u.account_id)
SELECT sum(amount) AS opex_2026
FROM ledger
WHERE fy = 2026 AND account_id IN (FROM under_opex);

-- duckent IV: attach the facts once, then one selector plus one aggregate
ATTACH ledger TO coa.account USING (account_id);
FROM ledger MATCH 'account#opex * entry[fy="2026"]' SELECT sum(amount);
